    总原则：

    编程语言模型的演进，本质上是：人类为了描述更复杂的现实，给语言加入新的表达能力；但每加入一种能力，都会制造新的复杂性，于是又需要新的组织机制去约束它。

    也就是：

    表达能力增强
    ↓
复杂性上升
    ↓
需要新的约束和组织方式
    ↓
形成新的语言模型

    一、第一性原理起点：程序到底在干什么？

    从最底层看，程序只做三件事：

    1. 表示东西
2. 计算东西
3. 改变东西

    对应到语言里，就是：

    表示东西：
    value / type / variable

计算东西：
    operator / expression / function

改变东西：
    state / assignment / effect / interaction

    所以语言最核心的五个块就是：

    type
variable
function
operator
expression

    这些是最小砖块。

    但是，光有砖块还不够。真正的问题是：

    我们怎么组织这些砖块，才能描述越来越复杂的现实？

    于是模型开始演进。

    二、第一层：只描述“关系和结果” —— Declarative Model

    如果世界很简单，我们只想表达：

    我要什么结果？
什么关系成立？
什么规则成立？

    那就得到声明式模型。

    声明式模型的第一性原理是：

    把程序看成“关系 / 规则 / 结果”的描述，而不是一步一步的状态修改。

    比如：

    我要所有年龄大于 18 的用户。

    而不是：

    先创建数组；
遍历所有用户；
判断年龄；
符合条件就 push；
最后返回数组。

    所以声明式模型的核心是：

    关注 what
弱化 how
弱化显式状态变化

    它的好处是：

    更容易推理；
更接近数学关系；
不容易被执行顺序干扰。

    但它的问题是：

    现实世界不只是静态关系；
现实世界有变化、有交互、有时间、有失败、有并发。

    于是继续演进。

    三、第二层：让推理更可靠 —— Pure Functional Model

    声明式模型已经在弱化状态变化，但还可以再进一步：

    如果变量不变，函数没有副作用，那程序就更容易推理。

    这就是纯函数模型。

    它的第一性原理是：

    把计算看成确定的输入到输出的映射。

    也就是：

    same input → same output

    所以它自然强调：

    immutability：数据不可变
pure function：函数无副作用
higher-order function：函数可以作为值传递
function composition：用函数组合构建程序
monad / effect wrapper：把副作用显式包起来

    为什么需要高阶函数？

    因为很多流程是重复的：

    遍历
过滤
映射
聚合
错误传播
异步组合

    如果函数可以作为参数，就可以把这些公共流程抽出来。

    为什么需要 Monad？

    因为现实世界有：

    IO
错误
空值
异步
外部状态

    纯函数模型不想让这些东西污染普通计算，所以把它们放进一个显式上下文里。

    所以纯函数模型的本质是：

    最大限度降低状态和副作用，让程序更像可组合的数学计算。

    但问题是：

    现实世界不只是纯计算；
很多事情是同时发生的。

    于是进入并发。

    四、第三层：现实是同时发生的 —— Concurrent Declarative Model

    现实中很多事情不是一个接一个发生，而是同时存在：

    用户请求
网络 IO
文件读写
后台任务
传感器数据
服务响应

    所以语言需要表达：

    多个计算任务可以同时存在。

    于是加入：

    thread

    这形成：

    Concurrent Declarative Model
并发声明式模型

    它的第一性原理是：

    把独立计算放到不同执行线里，让它们可以并发存在。

    它解决了：

    任务可以同时启动；
主线程可以等待结果；
可以通过 join 拿最终结果。

    但它不解决：

    任务之间怎么持续通信？
谁负责关闭？
谁负责取消？
谁处理错误？
谁管理长期状态？

    所以仅有 thread 不够。

    于是引入消息传递。

    五、第四层：并发任务要合作 —— Message Passing Model

    多个任务同时存在之后，必然要合作。

    合作就需要通信。

    最危险的通信方式是：

    大家一起改共享变量。

    这会带来数据竞争、锁、死锁、状态混乱。

    所以另一种思路是：

    不要共享内存来通信，而是通过消息通信。

    于是出现：

    message
channel
port
select

    Message Passing 的第一性原理是：

    任务之间不直接共享内部状态，而是通过消息交换信息。

    这带来了：

    producer-consumer
pipeline
fan-in
fan-out
worker pool
done channel

    它解决的是：

    并发任务之间如何传数据；
如何同步；
如何建立数据流；
如何减少共享可变状态。

    但它还有问题：

    channel 谁创建？
谁关闭？
任务生命周期谁管？
出错了谁恢复？
长期运行的服务状态放哪里？

    于是进一步抽象。

    六、第五层：长期并发状态要变成服务 —— Actor Model

    有些并发任务不是“一次性计算”，而是长期存在：

    聊天房间
订单服务
日志服务
数据库连接池
机器人导航服务
报警服务

    它们有自己的状态，并且长期接收请求。

    于是我们把 thread/task 提升成：

    actor / service-like entity

    Actor 的第一性原理是：

    把长期存在的并发状态封装成一个有身份、有邮箱、有私有状态的服务实体。

    Actor 是：

    identity
mailbox
private state
message handler
supervisor
name service

    外部不是直接改它的状态，而是：

    send message → actor mailbox

    Actor 自己：

    接收消息
读取当前状态
计算新状态
进入下一轮

    所以你说它像有限状态机，这个理解是对的。

    Actor 解决：

    长期并发状态归谁管理；
消息如何进入；
服务如何被定位；
失败后谁监督恢复。

    到这里，并发路线先不深入。

    现在回到另一个主线：状态。

    七、第六层：现实会变化 —— Explicit State Model

    声明式和函数式模型都尽量弱化状态变化。

    但现实世界大量东西就是会变：

    账户余额会变
订单状态会变
库存会变
文件指针会变
用户登录状态会变
机器人位置会变

    所以语言引入一个关键能力：

    mutable variable
assignment

    也就是：

    x = x + 1

    看起来只增加了“修改变量”的能力，但本质上是把 时间 引进了程序。

    因为现在：

    同一个变量，在不同时间可以有不同值。

    于是程序不再只是表达式求值，而变成：

    state0 → statement1 → state1 → statement2 → state2

    Explicit State Model 的第一性原理是：

    为了直接描述现实中的变化，语言引入可变状态。

    它带来的表达能力很强：

    循环
计数器
队列
缓存
状态机
文件读写
业务流程
资源生命周期

    但它也打开了潘多拉魔盒：

    执行顺序重要了；
变量有历史了；
函数可能有副作用了；
别名可能指向同一个对象；
状态可能半更新；
不变式可能被破坏；
异常可能留下脏状态；
并发下可能数据竞争。

    所以问题变成：

    状态太强了，必须被组织起来。

    于是长出 Procedure、Module、Object。

    八、第七层：把多步状态变化命名 —— Procedure

    显式状态之后，代码很容易变成一堆散落的步骤：

    检查余额
扣钱
加钱
记录日志
更新状态
处理异常

    如果每个调用方都手写这些步骤，就会乱。

    所以第一步组织方式是：

    Procedure

    Procedure 的第一性原理是：

    把一组有顺序的状态操作封装成一个有名字的动作。

    比如：

    transfer()
payOrder()
shipOrder()
createUser()

    Procedure 解决的是：

    不要让业务动作散落在调用方；
把正确顺序封装起来；
降低重复；
集中处理局部一致性。

    但 Procedure 还不够。

    因为程序变大后，会有很多 procedure：

    transfer()
deposit()
withdraw()
createAccount()
closeAccount()
validateAccount()

    这些东西放哪里？谁能调用？哪些是内部细节？

    于是需要 Module。

    九、第八层：给相关动作和状态一个边界 —— Module

    Module 的第一性原理是：

    把一组相关状态、过程、类型、常量和内部细节放进一个边界里。

    所以 Module 不只是“一堆函数”。

    它是：

    相关状态
相关 procedure
相关 type
相关 constant
public interface
private implementation
namespace

    一句话：

    Procedure 管一个动作。
Module 管一组相关动作和状态的边界。

    Module 解决：

    代码放哪里；
状态归哪个模块；
外部能访问什么；
内部细节怎么隐藏；
命名冲突怎么避免；
依赖边界怎么管理。

    但 Module 通常是静态边界。

    比如：

    account_module
order_module
payment_module

    它适合管理“一类功能”，但它不自然表达：

    张三的账户
李四的账户
订单 001
订单 002
机器人 A
机器人 B

    也就是：具体实体。

    于是需要 Object。

    十、第九层：状态属于具体实体 —— Object

    Object 的第一性原理是：

    现实中有很多具体实体，它们有身份，有自己的状态，并通过行为响应外部操作。

    所以 Object 是：

    identity + state + behavior

    它解决：

    状态到底属于谁？
谁能改这个状态？
这个实体现在是什么状态？
这个实体能响应什么操作？

    比如：

    account_001.balance
account_002.balance

    两个账户即使余额相同，也不是同一个账户。

    这就是 identity。

    Object 把显式状态进一步收束成：

    有身份的状态边界

    外部不应该随便改它的内部状态，而应该通过行为：

    account.withdraw()
account.deposit()
order.pay()
order.ship()

    这一步非常关键。

    因为它把“状态管理”从散落变量变成了：

    具体实体自己管理自己的状态。

    但 Object 多了之后，又出现新问题：

    很多对象结构相似；
很多对象行为相似；
怎么共享行为？
怎么统一创建？
怎么组织对象类型？

    于是出现两条路线。

    十一、第十层 A：对象委托对象 —— Object-based / Prototype-based

    第一条路线是：

    不先定义类型，直接让对象委托对象。

    这就是 prototype-based。

    它的第一性原理是：

    行为可以放在另一个对象上，共享给多个对象；具体状态留在每个对象自己身上。

    比如：

    accountA 委托 accountPrototype
accountB 委托 accountPrototype

    查找逻辑是：

    对象自己没有方法
    ↓
去 prototype 找
    ↓
再沿 prototype chain 往上找

    关键点：

    方法在 prototype 上；
this 指向实际调用者；
共享行为，独立状态。

    优点：

    灵活；
动态；
对象可以运行时扩展；
不需要提前设计 class。

    缺点：

    结构隐式；
初始化约束隐式；
方法依赖哪些字段不清楚；
this 容易出问题；
心智负担高。

    所以 Prototype 的本质是：

    用对象委托解决行为共享。

    十二、第十层 B：类型模板创建对象 —— OOP / Class-based

    第二条路线是：

    先定义一类对象的模板，再创建具体对象。

    这就是 class-based OOP。

    Class 的第一性原理是：

    把一类对象共同的结构、初始化规则和行为集中描述出来。

    Class 定义：

    字段结构
初始化规则
方法集合
对象不变式
对外接口

    Instance 是：

    class 创建出来的具体对象。

    所以：

    Object：
    一个具体实体。

Class：
    一类对象的模板。

Instance：
    由 class 创建出来的具体实体。

    OOP 进一步发展出：

    encapsulation
inheritance
polymorphism
interface
abstract class
subtyping
dynamic dispatch

    这些不是孤立概念，而是为了解决 class-based object system 的复杂性。

    十三、第十一层：封装 —— 控制状态入口

    可变状态最危险的问题是：

    谁都能改。

    封装的第一性原理是：

    对象内部状态不能被外部随意修改，外部必须通过对象提供的行为进入。

    所以：

    private state
public method

    本质不是语法，而是：

    控制状态修改入口；
维护对象不变式；
隐藏内部实现；
让对象自己负责自己的合法性。

    一句话：

    封装 = 管住状态。

    十四、第十二层：继承 —— 复用和扩展类型

    当 class 多了之后，会出现相似类型：

    Animal → Dog / Cat
Shape → Circle / Rectangle
Account → CreditAccount

    继承的第一性原理是：

    如果一个类型确实是另一个类型的特殊化，可以复用并扩展父类型的结构和行为。

    继承解决：

    类型之间的代码复用；
共同逻辑上提；
子类扩展或重写行为。

    但继承很危险。

    因为它不仅复用代码，还继承了：

    父类状态
父类方法
父类假设
父类不变式
父类行为契约

    所以继承不是简单的“复用代码工具”。

    它更像：

    类型承诺。

    这就引出 subtyping 和 LSP。

    十五、第十三层：多态和动态分派 —— 统一调用，不同行为

    当有很多子类型时，调用方不想写：

    if Dog
if Cat
if Cow

    于是需要多态。

    Polymorphism 的第一性原理是：

    调用方只依赖共同抽象，具体对象自己决定如何响应。

    比如：

    animal.speak()
payment.pay()
shape.area()

    调用方只知道：

    你能 speak / pay / area

    不关心你具体是谁。

    Dynamic Dispatch 是多态的运行机制：

    编译期看静态类型能不能调用；
运行期看真实类型执行哪个实现。

    所以：

    Subtyping：
    谁能放到抽象位置。

Dynamic Dispatch：
    放进去之后执行哪个方法。

Polymorphism：
    统一调用形成不同行为。

    十六、第十四层：Interface 和 Abstract Class —— 抽象能力与共同基础

    Interface 的第一性原理是：

    调用方应该依赖对象能做什么，而不是对象具体是谁。

    所以 interface 是：

    能力契约
can-do

    比如：

    PaymentMethod.pay()
Runnable.run()
Comparable.compareTo()

    Abstract class 的第一性原理是：

    某些类型确实共享一部分状态和实现，但还需要子类补完。

    所以 abstract class 是：

    带部分实现的公共父类
is-a 的共同基础

    区别：

    interface：
    你能做什么？

abstract class：
    你是什么的一种，并共享部分基础？

    十七、第十五层：LSP —— 继承关系必须可信

    继承会让编译器允许：

    父类变量 = 子类对象

    但这不代表行为上一定正确。

    LSP 的第一性原理是：

    如果调用方相信父类契约，那么子类替换进去后不能破坏这个契约。

    也就是：

    子类不能要求更多；
子类不能承诺更少；
子类不能破坏父类不变式；
子类不能让调用方原本正确的代码变错。

    LSP 解决：

    继承关系是不是在骗人？
子类到底能不能安全替代父类？
父类抽象是否可信？

    如果不满足 LSP：

    多态失效；
调用方被迫判断具体类型；
继承关系应该重构。

    十八、第十六层：组合优于继承 —— 降低耦合

    继承是强关系：

    is-a

    组合是弱关系：

    has-a / use-a

    组合优于继承的第一性原理是：

    如果你只是想复用能力或替换行为，就不要建立沉重的血缘关系。

    比如：

    OrderService has PaymentMethod

    比：

    OrderService extends AliPay

    合理得多。

    继承适合：

    稳定 is-a 关系
并且满足 LSP

    组合适合：

    复用能力
替换策略
装配组件
降低耦合

    所以：

    继承表达身份关系；
组合表达协作关系。

    十九、第十七层：DIP / OCP / ISP / SRP —— 应对变化

    大型系统真正可怕的不是“写不出来”，而是：

    一变就坏。

    所以 OOP 原则本质上都在处理变化。

    DIP：依赖倒置

    第一性原理：

    稳定的高层业务不应该依赖易变的具体实现。

    所以：

    高层依赖抽象；
低层实现抽象。

    它带来：

    低耦合
可替换
可测试
支持扩展

    OCP：开闭原则

    第一性原理：

    稳定代码不要因为每个新增变体都反复修改。

    所以：

    对扩展开放；
对修改关闭。

    新增支付方式时，新增类，而不是改订单服务。

    ISP：接口隔离

    第一性原理：

    调用方不应该被迫依赖自己用不到的能力。

    所以接口要小而专一。

    胖接口会导致：

    实现类被迫实现无关方法；
调用方依赖过多；
变化扩散。

    SRP：单一职责

    第一性原理：

    不同变化原因不应该绑在同一个类里。

    一个类承担太多职责，就会因为太多原因被迫修改。

    二十、最终第一性原理总图

    你可以把整个过程压成一条链：

    人类要表达计算
    ↓
Core：类型、变量、函数、操作符、表达式

人类想描述结果和规则
    ↓
Declarative：描述 what，而不是 how

人类想让推理更可靠
    ↓
Functional：不可变、纯函数、副作用显式化

人类要模拟同时发生的现实
    ↓
Concurrent Declarative：thread / join

并发任务要合作
    ↓
Message Passing：message / channel / select

长期并发状态要被服务化管理
    ↓
Actor：mailbox + state + supervisor

人类要直接表达现实变化
    ↓
Explicit State：mutable variable / assignment / loop

状态操作太分散
    ↓
Procedure：把多步状态变化封装成动作

动作和状态太多
    ↓
Module：给相关状态和动作建立边界

需要表达具体实体
    ↓
Object：identity + state + behavior

相似对象要共享行为
    ↓
Object-based：prototype delegation

    二十一、最重要的一句话

    归结成这一句：

    语言模型的演进，不是为了堆概念，而是为了在“表达现实复杂性”和“控制程序复杂性”之间不断寻找平衡。

    更短一点：

    表达力越强，复杂性越高；
复杂性越高，越需要边界、抽象和约束。

    所以：

    Declarative 控制过程复杂性；
Functional 控制副作用复杂性；
Message Passing 控制并发通信复杂性；
Actor 控制长期并发状态复杂性；
Explicit State 引入现实状态变化；
Procedure / Module 控制状态操作复杂性；
Object 控制实体状态复杂性；
OOP 控制对象类型复杂性；
SOLID 控制大型系统变化复杂性。

    这就是从第一性原理拆出来的完整主线。
